## Задание на архитектуру системы
- Источники данных для системы — SHOP API и CLIENT API. SHOP API позволяет магазинам отправлять данные о товарах, CLIENT API предоставляет пользователям сервиса возможность выполнять запросы.
- Связывать все сервисы платформы и обеспечивать надёжную передачу данных будет Apache Kafka. Данные от магазинов (SHOP API) будут попадать в кластер Kafka. Для безопасной передачи данных кластер планируется настроить с использованием TLS. Данные записываются в топики, которые должны быть закрыты для записи другим клиентам.
- Для повышения надёжности и отказоустойчивости системы планируется реализовать репликацию данных, а также дублировать данные на второй кластер.
- Аналитическая система будет перекладывать данные из второго кластера Kafka в Data Lake, реализованный на базе HDFS (Hadoop Distributed File System). На основе этого Data Lake тимлид и архитектор предлагают развернуть платформу Apache Spark, которая будет выполнять аналитические вычисления.
- Обработчик в реальном времени должен проверять данные от магазинов и пропускать только разрешённые товары. Товары из списка запрещённых нужно фильтровать, обрабатывать их не надо. Обработчик будет подключён к основному кластеру Apache Kafka.
- Для обеспечения надёжности и отслеживания производительности кластера Kafka нужно реализовать мониторинг; планируется интеграция с Prometheus и Grafana.
- Для тестирования и отладки функций сервисов нужно организовать хранилище данных.

## Как это работает

## Инфра
Вся инфраструктура автоматически поднимается через docker compose и систему init контейнеров. Руками ничего делать не нужно, просто запускается make all и все само билдится\поднимается. Соответствующие конфигурационные файлы, скрипты настройки, сертификаты, json cхемы и прочее-прочее лежит в infra/**

Единственное - hadoop стартует довольно долго, поэтому перед взаимодействием с системой нужно подождать пару минут. Отслеживать, готова ли система, можно вызвав скрипт:
```bash
./scripts/is-ready.sh
```

## Взаимодействие с системой
Для запросов написаны скрипты, лежащие в директории ./scripts/**

- `put-products.sh` — отправляет все продукты из папки `products/` в Kafka
- `find-product.sh <name>` — ищет продукт по имени через CLIENT API и записывает клиентский запрос в Kafka
- `block-tags.sh <tag> [true|false]` — блокирует (или разблокирует) тег товара; заблокированные товары фильтруются в потоковой обработке
- `get_recommendations.sh` — получает список рекомендованных products из аналитической системы
- `select-products.sh` — выводит все products из PostgreSQL
- `select_client_requests.sh` — выводит все клиентские запросы из PostgreSQL
- `is_ready.sh` — проверяет готовность аналитического сервиса

Когда ```./scripts/is-ready.sh``` возвращает ОК, можно приступать к работе:

1. Вызвать ```./scripts/put-products.sh```, это отправит все продукты из папки **examples** в кафку
2. Вызвать ```./scripts/find-product.sh клавиатура``` и затем ```./scripts/find-product.sh часы```. Это вернет найденный продукт из базы + запишет данные по клиентскому запросу для дальнейшей аналитики. Поиск происходит по подстроке в имени продукта
3. При желании можно вызвать ```./scripts/block-tags.sh гаджеты```, для блокировки товаров по тегам
4. Далее можно смотреть в UI и в postgres. Рекомендации в зеркалированный кластер кафки запишутся с некоторой задержкой и будут доступны не сразу, для просмотра можно вызвать ```./scripts/get-recommendations.sh```. Рекомендации выдаются по принципу "собираем все запросы пользака, находим все продукты с похожими именами, выдаем их все"

## Как проверять работоспособность

Наличие данных в postgresql можно проверить вызвав скрипты ```./scripts/select-products.sh``` и ```./scripts/select-client-requests.sh```

Наличие данных в топиках kafka можно проверить через KafkaUI сервис для соответствующего кластера (основной или зеркало)

### Адреса UI сервисов:

- `http://localhost:3000` — Grafana (дашборды мониторинга Kafka)
- `http://localhost:9090` — Prometheus (метрики)
- `http://localhost:9093` — Alertmanager
- `http://localhost:8085` — Kafka UI (основной кластер)
- `http://localhost:8086` — Kafka UI (зеркальный кластер)
- `http://localhost:8083` — Kafka Connect REST API
- `http://localhost:8087` — Debezium UI
- `http://localhost:9870` — Hadoop Namenode UI
- `http://localhost:4040` — Spark UI
- `http://localhost:8080` — CLIENT API (find-product, recommendations)

## Явные недостатки

* Библиотека для работы со Spark у Go очень сырая, и функционал там кастрированный. Поэтому обработчик реализовал как получилось. Обработанные рекомендации отсылаются через простой producer в топик recommendations, поскольку через либу это сделать сейчас невозможно. Сообщения льются постоянно, без идемпотентности, и они копятся, даже если рекомендации не изменились. Проблему вижу но решил не усложнять
* Для упрощения записи в базу, вложенные объекты из изначальной схемы product уплощаются в строки и кладутся в базу
* client api для получения рекомендаций подписывается на топик из зеркального кластера. Наверное, не лучшее решение, но в задании как будто именно это и требуется. Ksql решил пока не юзать и не усложнять
* Код безобразный, плохо организован, не разбит на разные слои и не использует интерфейсы. Пока плохо представляю, как с такими пестрыми гошными API для работы с kafka, hadoop, spark грамотно организовать структуру
